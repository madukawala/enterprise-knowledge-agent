# Standing Orders and Scheduled Payments

## Overview

Standing orders and scheduled payments let customers set up payments that go out on a future date, either once or on a repeating basis. Typical uses are rent, savings transfers, pocket money and paying a regular supplier.

This specification covers the move of standing orders from CoreLedger onto PayHub and Scheduler, so that all outgoing payments follow the same path and get the same status tracking.

## Customer problem and goals

Customers rely on standing orders for important bills like rent. When one fails, the consequences can be serious. Problems with the old service included:

- payments failing silently, with customers only finding out from the payee;
- no easy way to change the amount or skip a single payment;
- payments due on weekends and bank holidays being handled inconsistently.

Goals:

- every due payment is attempted on the due date, or the next working day where the customer chose that;
- customers are told if a payment fails, and why, on the same day;
- customers can create, change, pause and cancel payments in Helix Mobile and Helix Online.

## Features

- **One-off scheduled payment** for a date up to one year ahead.
- **Standing orders** weekly, every two weeks, monthly, quarterly or yearly, with an optional end date or number of payments.
- **Change or skip** the next payment without cancelling the standing order.
- **Weekend and bank holiday handling**: payments due on a non-working day go on the next working day by default. Customers can choose the previous working day instead.
- **Insufficient funds retry**: if there is not enough money, the payment is retried at 14:00 the same day. If it still fails, the customer is notified.
- **Failure notifications** by push notification and in the app.
- **History** of every payment made under a standing order.

## Limits and fees

| Item | Amount |
|---|---|
| Fee to set up, change or cancel | Free |
| Maximum payment amount (personal) | GBP 25,000 per payment |
| Maximum payment amount (business) | GBP 100,000 per payment |
| Maximum active standing orders per account | 100 |
| Cut-off for changes | 23:59 the day before the due date |
| Unpaid standing order fee | None |

## Systems involved

| System | Role |
|---|---|
| Helix Mobile and Helix Online | Set-up and management screens. |
| Scheduler | Holds the schedule and runs the daily 06:00 run, creating payment instructions in PayHub for everything due that day. Runs a 14:00 retry run. |
| PayHub | Processes each payment instruction. |
| Instant Payments Gateway | Sends payments to FastLane. |
| CoreLedger | Holds balances. The end-of-day batch must finish by 05:30 so that the 06:00 run uses correct balances. |
| Payment Status Service | Updates statuses and sends failure notifications. |

## Run timings

| Run | Time | Purpose |
|---|---|---|
| Main run | 06:00 | Creates instructions for all payments due today. Must complete by 07:30. |
| Retry run | 14:00 | Retries payments that failed for insufficient funds. |
| Reconciliation | 18:00 | Checks every due instruction has a final status. |

## Non-functional requirements

- The 06:00 run must process up to 400,000 standing orders, the peak on the first working day of the month, by 07:30.
- If the 06:00 run fails, it must be safe to rerun without creating duplicate payments. Each instruction carries a unique key made from the standing order ID and due date.
- Scheduler configuration, such as run times, batch size and retry rules, must be version controlled and changed through the pipeline with peer review, in line with POL-005.
- Alerts must fire if the 06:00 run has not started by 06:05 or has not finished by 07:30.

## Open questions

1. Should the 14:00 retry also apply to scheduled one-off payments?
2. What happens if the CoreLedger end-of-day batch overruns past 06:00? Do we delay the Scheduler run or run with the previous day's balances? Core Banking to propose an approach.
3. Can we offer a "pay on the last working day of the month" option?
4. How do we safely test a configuration change to a run that only happens once a day? Options include a dry run against a copy of the schedule.
