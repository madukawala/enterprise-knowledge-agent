# Card Authorisation Failure Triage

## Purpose

When card payments start failing, the first 15 minutes matter most. This runbook gives the Cards Platform on-call engineer a fixed order of checks to find out where in the authorisation path the failure sits, so the right specialist runbook can be used.

It was written after two card outages in 2025: INC-2025-022 in July (an HSM firmware update broke PIN checks) and INC-2025-041 on 3 December (an expired mTLS certificate at the Network Gateway). In both cases engineers spent too long looking at the wrong component.

## When to use this runbook

- Card approval rate drops more than 5 percentage points below the same hour last week.
- Spike in a single decline code.
- Merchants, customers or the contact centre report cards being declined.

## Symptoms and alerts

| Alert | Source |
|---|---|
| `CardSwitchApprovalRateLow` | Prometheus, pages Cards Platform on-call |
| `CardSwitchNetworkHandshakeFailures` | Prometheus |
| `HsmResponseErrors` | Prometheus |
| `SentinelDeclineRateHigh` | Prometheus, also goes to Fraud and Security |

## Checks

Work through these in order. Stop when you find the failing component.

1. **Scope.** On the Grafana dashboard "CardSwitch Authorisations", split by site, channel (chip, contactless, card-not-present) and network. Is it one site, one channel or everything?
2. **Network Gateway.** Look for TLS handshake errors and decline code 91. Check certificate expiry on both sites:
   ```
   openssl s_client -connect ngw-primary.cards.internal:8443 </dev/null 2>/dev/null | openssl x509 -noout -enddate
   ```
   If the certificate has expired or the chain is broken, go to RB-002.
3. **HSM.** On "HSM Health", check response errors and latency. PIN failures with decline code 55 across many cards point to the HSM, not the customers.
4. **Sentinel.** On "Sentinel Decisions", check whether fraud declines (decline code 59) have jumped. If only card-not-present is affected, Sentinel is the likely cause. Contact Fraud and Security; do not change fraud settings yourself.
5. **CardSwitch itself.** Check pod health, error logs and recent releases:
   ```
   kubectl -n cards get pods -l app=cardswitch
   ```
6. **CoreLedger.** Debit card authorisations need a balance check. If CoreLedger is slow, decline code 91 may come from our side. Check "CoreLedger API" latency.
7. **Recent changes.** Check the change calendar and configuration audit log for anything in the last 24 hours.

## Steps to fix

1. Open an incident as soon as customer impact is confirmed. Card outages are normally SEV1 when all channels are affected. Follow RB-009 for status page updates.
2. If one site is failing, move traffic to the healthy site:
   ```
   cardswitchctl site drain --site secondary
   ```
   Check the healthy site has capacity on "CardSwitch Capacity" first.
3. Apply the fix from the specialist runbook (RB-002 for certificates) or roll back a recent release.
4. Turn on stand-in processing at the network only with the Cards product owner's agreement, because stand-in limits apply and fraud checks are reduced.
5. Confirm the approval rate is back to normal for 15 minutes before closing the bridge.
