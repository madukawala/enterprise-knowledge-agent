# Suspected Staff Account Compromise Response

## Purpose

This runbook covers what the Security Operations analyst and Fraud and Security on-call engineer do when a staff HelixID account may be in the hands of someone else. The aim is to contain access quickly, keep evidence and find out what the attacker touched.

It is restricted because it describes our detection rules and containment tools. Do not copy it into team wikis or tickets visible to all staff.

## When to use this runbook

- A member of staff reports entering their password on a suspicious page.
- HelixID raises an impossible travel or unusual device alert.
- Multi-factor push requests the user did not start (push fatigue).
- Mailbox rules created to forward or delete mail without the user's knowledge.
- Privileged activity from an account outside its normal pattern.

## Symptoms and alerts

| Detection | Source | Priority |
|---|---|---|
| `HID-IMPOSSIBLE-TRAVEL` | HelixID risk engine | High |
| `HID-MFA-FATIGUE` (5 or more denied pushes in 10 minutes) | HelixID | High |
| `MAIL-FWD-EXTERNAL` new forwarding rule to an outside domain | Mail security gateway | High |
| `PAM-OFFHOURS-ELEVATION` | Privileged access vault | Critical |
| User report to the security mailbox | Service desk | Medium, raise if credentials were entered |

## Checks

1. Confirm the account and the user's line manager. Call the user on a known number from the staff directory, not one given in an email.
2. In the HelixID admin console, review sign-ins for the last 72 hours: source addresses, devices, applications reached.
3. Check whether the account holds privileged roles in the privileged access vault (see POL-006). A privileged account raises the response to critical.
4. Check mailbox rules, delegated access and recent sent items.
5. Search the proxy and mail logs for the phishing link or sender, to find other staff who received it.

## Steps to fix

1. **Contain within 15 minutes of confirmation.**
   - Disable sign-in and revoke all sessions and refresh tokens:
     ```
     hidctl user disable --upn <user> --revoke-sessions
     ```
   - Reset multi-factor registrations so new methods must be enrolled in person or by video with ID check.
   - If privileged, check out and rotate every credential the account could reach in the vault.
2. **Preserve evidence.** Export HelixID sign-in logs, mailbox audit logs and endpoint telemetry to the evidence store under the case number. Do not wipe the laptop until Security agrees.
3. **Remove persistence.** Delete malicious mailbox rules, application consents and any new device registrations.
4. **Block the source.** Add the phishing domain and sender to the mail and web block lists. Pull the message from all mailboxes.
5. **Assess payment and customer data impact.** If the account could reach PayHub operator screens, CardSwitch tooling or customer data, ask Payments Operations or Cards Platform to review actions taken in that period.
6. **Restore access** only after the user has a new password, new multi-factor methods and a clean device.
7. **Report.** Raise an incident under POL-004. Inform the CISO for any privileged account or confirmed data access. Operational Risk decides on regulatory notification.
