# Renewing mTLS Certificates for the Network Gateway

## Purpose

CardSwitch talks to the card networks through the Network Gateway over mutual TLS. If the client certificate on our side expires, or the chain is incomplete, the networks drop the connection and every card authorisation is declined. This runbook covers planned renewal and emergency replacement.

It was written after INC-2025-041 on 3 December 2025, when the primary client certificate expired at 02:14 with no alert and card payments were declined for nearly three hours. Renewal had previously relied on one engineer's calendar reminder.

## When to use this runbook

- A planned renewal, started no later than 30 days before expiry.
- An expiry warning from the certificate inventory report.
- An emergency where card authorisations are failing with TLS handshake errors at the Network Gateway.

## Symptoms and alerts

- `CardSwitchNetworkHandshakeFailures` alert, or a sudden drop in approval rate on the Grafana dashboard "CardSwitch Authorisations".
- Network Gateway logs showing `certificate expired` or `unknown ca`.
- Decline code 91 (issuer or switch unavailable) rising sharply.
- Merchants and customers reporting declines at point of sale and online.

## Checks

1. Check the current certificate on each site:
   ```
   openssl s_client -connect ngw-primary.cards.internal:8443 -showcerts </dev/null | openssl x509 -noout -subject -enddate
   openssl s_client -connect ngw-secondary.cards.internal:8443 -showcerts </dev/null | openssl x509 -noout -subject -enddate
   ```
2. Confirm the full chain is presented (leaf, intermediate, root). The intermediate must be in the bundle on both sites.
3. Compare serial numbers on primary and secondary. They must match after a renewal.
4. Check the certificate inventory spreadsheet and the vault entry `cards/ngw/client-cert` for the expected expiry date.

## Steps to fix

### Planned renewal

1. Raise a standard change at least 10 working days before the target date. Attach this runbook as the implementation plan and a rollback plan.
2. Generate a new key pair inside the HSM partition `CARDS-NGW`. The private key must never leave the HSM.
3. Create the certificate signing request and send it to the card network certificate portal through the Cards Platform service account. Two people must approve the request.
4. When the signed certificate arrives, build the bundle with the intermediate and store it in the vault at `cards/ngw/client-cert` as a new version.
5. Deploy to the secondary site first, during the low-traffic window (02:00 to 04:00).
6. Run the test authorisation using the internal test card range and confirm approval.
7. Deploy to the primary site and repeat the test.
8. Run the checks above on both sites and record the serial numbers and expiry dates in the change ticket.
9. Update the certificate inventory and set reminders at 60, 30 and 7 days before the next expiry.

### Emergency replacement

1. Declare a SEV1 and page the major incident manager. Follow RB-009 for status page updates.
2. If a renewed certificate already exists in the vault but was not deployed, deploy it to the failing site straight away using the emergency change route.
3. If no valid certificate exists, contact the card network's 24-hour support line (number in the Cards Platform on-call handbook) and request an expedited signing.
4. Restart the Network Gateway connectors one site at a time:
   ```
   kubectl -n cards rollout restart deploy/ngw-connector
   ```
5. Confirm approval rates return to normal on the "CardSwitch Authorisations" dashboard.
