# Rolling Back a Bad Configuration Change

## Purpose

Many of our systems change behaviour through configuration rather than code: payment routing rules, fraud thresholds, scheduler settings and feature flags. A wrong value can break customer payments as badly as a code defect. This runbook explains how to find the change that caused a problem and how to roll it back safely.

It was written after INC-2026-007 on 17 February 2026, when a routing rule change for instant payments went straight to production and caused rejections for about 90 minutes. Finding which change was responsible took 40 minutes of that time. The Change Advisory Board discussed the incident on 19 March 2026 (MTG-003).

## When to use this runbook

- Errors or declines start shortly after a configuration change.
- A system behaves differently but no code was released.
- A change owner asks for help undoing their change.

## Symptoms and alerts

- A sudden step change, not a gradual rise, in error or decline rates on any payments or cards dashboard.
- The Grafana annotation layer "Config changes" shows a change within 30 minutes of the step.
- New rejection reason codes appear that were not seen before.

## Checks

1. Open the configuration service audit log and list changes in the last two hours:
   ```
   cfgctl audit --since 2h --env prod
   ```
2. Match the time of each change to the start of the problem on the relevant dashboard.
3. Check the change ticket for the change. Note whether it had a canary stage and a rollback plan.
4. Check whether more than one change went out together. If so, roll back the most recent first.
5. Confirm with the change owner, if they can be reached within 5 minutes. Do not wait longer than that if customers are affected.

## Steps to fix

1. Open an incident if customers are affected and follow RB-009 for communications.
2. Roll back to the previous version of the setting:
   ```
   cfgctl rollback --key <config key> --to-version <previous> --env prod --reason "<incident id>"
   ```
   The configuration service keeps the last 20 versions of each key.
3. For settings held in Kubernetes ConfigMaps rather than the configuration service, re-apply the previous version from the configuration repository and restart the affected deployment:
   ```
   kubectl -n <namespace> apply -f <previous configmap>
   kubectl -n <namespace> rollout restart deploy/<service>
   ```
4. Confirm on the dashboard that the error rate returns to its normal level within 10 minutes.
5. Freeze further changes to the same component until the post-incident review is complete.
6. Record the rollback in the original change ticket and link the incident.
7. If the rollback does not fix the problem, the change was probably not the cause. Re-open the investigation rather than rolling back other changes at random.

## Prevention

The Change Advisory Board (MTG-003) has proposed a revision of POL-005. Until it is approved, teams are asked to follow it now. Every configuration change to production should:

- go to a canary first, taking 5% of traffic for at least 30 minutes,
- have a written rollback plan with the exact command,
- be announced in the change channel before it starts.
