# Kafka Consumer Lag in the Payment Status Service

## Purpose

The Payment Status Service (PSS) reads payment events from the Kafka topic `payments.status`, updates the status customers see and sends notifications. If the consumers fall behind, payments that have in fact completed still show as "pending". Customers then try again and send the same payment twice.

This runbook was written after INC-2026-017 on 22 April 2026. Consumer lag reached about 1.2 million messages, statuses were stuck for over two hours, and 640 customers made duplicate payments that had to be recalled.

## When to use this runbook

- Consumer lag alert on `pss-consumer`.
- Customers or the contact centre report payments stuck at "pending".
- Notifications are arriving late or not at all.

## Symptoms and alerts

| Alert or signal | Threshold | Source |
|---|---|---|
| `PssConsumerLagHigh` | lag above 50,000 for 5 minutes | Prometheus |
| `PssConsumerLagCritical` | lag above 250,000 or rising for 15 minutes | Prometheus, pages on-call |
| Status update age | p95 above 2 minutes | Grafana "Payment Status Service" |
| Duplicate payment check hits | more than 20 per hour | Grafana "Payment Status Service" |

## Checks

1. Check lag per partition:
   ```
   kafka-consumer-groups --bootstrap-server kafka.payments.internal:9093 --describe --group pss-consumer
   ```
   If lag is on one or two partitions only, a stuck consumer or a poison message is likely. If it is on all partitions, the consumers are under-scaled or the downstream is slow.
2. Check consumer pod health and restarts:
   ```
   kubectl -n pss get pods -l app=pss-consumer
   ```
3. Check the notification provider latency and the PSS database write latency on the dashboard. Slow downstream calls block the consumers.
4. Check whether a PSS release went out in the last 24 hours.
5. Look in the dead-letter topic `payments.status.dlq` for repeated failures on the same message.

## Steps to fix

1. If customers are affected, open an incident and post a status page update using RB-009. Ask the contact centre to tell customers not to resend payments.
2. If a recent release is suspected, roll it back:
   ```
   kubectl -n pss rollout undo deploy/pss-consumer
   ```
3. If one partition is stuck on a bad message, move it to the dead-letter topic using the PSS admin tool:
   ```
   pssctl skip --partition <n> --offset <offset> --to-dlq
   ```
   Record the offset in the incident ticket so the message can be replayed later.
4. If lag is on all partitions and downstream is healthy, scale the consumers up to the partition count (currently 24):
   ```
   kubectl -n pss scale deploy/pss-consumer --replicas=24
   ```
5. If notifications are the bottleneck, switch notifications to batched mode with the flag `pss.notify.batch=true` so status updates can catch up first.
6. Watch lag until it is under 5,000, then return replicas and flags to normal.
7. Ask Payments Operations to run the duplicate payment report for the affected window and start recalls where needed.
