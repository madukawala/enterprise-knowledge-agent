# End-of-Day Batch Overrun

## Purpose

CoreLedger runs the end-of-day (EOD) batch every night. It posts the day's transactions, calculates interest, produces statement data and rolls the ledger to the next business date. The batch must finish by 05:30 so that balances are correct when Helix Mobile and Helix Online traffic picks up, and so that the Scheduler's 06:00 standing order run works against the new business date.

This runbook tells the Core Banking on-call engineer what to do when the batch is running late. It replaces the older notes kept on the team wiki, which assumed the batch window ended at 06:00.

## When to use this runbook

- The batch has not reached the interest stage by 03:30.
- The batch monitor predicts a finish after 05:00.
- A batch job has failed and been restarted.
- Month-end and quarter-end nights, when volumes are about 40% higher.

## Symptoms and alerts

| Alert | Meaning |
|---|---|
| `EodMilestoneMissed` | A stage has not finished by its milestone time |
| `EodPredictedOverrun` | Projected finish time after 05:00 |
| `EodJobFailed` | A job ended with a non-zero return code |
| Long-running lock waits on `ledger_postings` | Batch competing with online traffic |

The milestones are on the Grafana dashboard "CoreLedger EOD":

| Stage | Expected finish |
|---|---|
| Transaction posting | 01:45 |
| Interest calculation | 03:15 |
| Statement extract | 04:30 |
| Date roll | 05:00 |

## Checks

1. Open "CoreLedger EOD" and identify which stage is behind.
2. Compare tonight's record counts with the previous four weeks. A large jump usually means a late bulk file or a duplicate feed.
3. Check for blocking sessions on the ledger database:
   ```sql
   SELECT blocked.pid, blocking.pid AS blocking_pid, left(blocked.query, 80)
   FROM pg_stat_activity blocked
   JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));
   ```
4. Check whether any reporting jobs or ad hoc queries are running against the primary database. These should run on the reporting replica.
5. Check storage and CPU on the batch servers.

## Steps to fix

1. If a job has failed, read its log in the batch console and restart it from its last checkpoint:
   ```
   eodctl restart --job <job name> --from-checkpoint
   ```
   Never restart the posting stage from the beginning without Core Banking lead approval, as this can double-post.
2. Stop any non-essential reporting or extract jobs on the primary database.
3. If online traffic is blocking the batch, ask Site Reliability to enable the overnight read-only banner for non-essential Helix Online features.
4. If the date roll will be later than 05:30, tell Payments Platform so the Scheduler run at 06:00 can be held. Do not let the Scheduler run against the old business date.
5. Tell Payments Operations and the contact centre that overnight balances and statements may be delayed. If customers will notice, follow RB-009.
6. When the batch completes, run the reconciliation check:
   ```
   eodctl reconcile --business-date <date>
   ```
7. Record the overrun, the cause and the finish time in the batch log.
