# PayHub Database Connection Pool Exhaustion

## Purpose

This runbook tells the on-call engineer how to recognise and recover from connection pool exhaustion between the PayHub services and the `payhub-db` Postgres database. It was written as a follow-up to INC-2026-003 (salary-day failures on 30 January 2026) and INC-2026-009 (month-end bulk payment delays on 27 February 2026). Both incidents had the same shape: the pool filled at peak, requests queued for a connection, and payments timed out. An earlier warning sign was the quarter-end slowdown in INC-2025-031.

## When to use this runbook

Use it when PayHub is slow or failing and the database is the likely bottleneck. It is most likely on:

- salary day (last working day of the month, and the 15th for some business customers)
- month-end and quarter-end
- the morning after a bank holiday, when the 06:00 Scheduler run is larger than usual

Do not use it for FastLane timeouts (see RB-003) or status updates stuck at pending (see RB-004).

## Symptoms and alerts

| Alert or signal | Where | Meaning |
|---|---|---|
| `PayHubDbPoolSaturation` (pool usage above 90% for 3 minutes) | Prometheus, pages Payments Platform on-call | Pool close to full |
| `PayHubConnectionWaitHigh` (p95 wait above 500 ms) | Prometheus | Threads waiting for a connection |
| Rising HTTP 503 and 504 rates on `/payments` | Grafana "PayHub Overview" | Customers seeing failures |
| `Connection is not available, request timed out` in logs | Log search, service `payhub-orchestrator` | Pool timeout reached |

Customers usually report "payment could not be completed" in Helix Mobile, and bulk payment files sit in "processing" for business customers.

## Checks

1. Open the Grafana dashboard "PayHub Database" and check active, idle and pending connections per pod group.
2. Check whether the database itself is struggling. If CPU on `payhub-db` is above 85% the problem is load, not just pool size.
3. Look for long-running queries:
   ```sql
   SELECT pid, now() - query_start AS runtime, state, left(query, 120)
   FROM pg_stat_activity
   WHERE datname = 'payhub' AND state <> 'idle'
   ORDER BY runtime DESC LIMIT 20;
   ```
   In both incidents the worst offender was a scan on `payment_instructions` filtering on `status` and `value_date`. An index for this query was added on 6 February 2026, so if this query shows up again, check the index is still being used (`EXPLAIN`) before anything else.
4. Confirm whether a bulk file or the Scheduler run started just before the alert.
5. Check recent deployments to PayHub in the release calendar. A new release that holds connections longer will look the same.

## Steps to fix

1. Declare an incident in the incident channel if failures are customer-facing. Follow RB-009 for communications.
2. If a single query is holding many connections for more than 60 seconds, cancel it:
   ```sql
   SELECT pg_cancel_backend(<pid>);
   ```
   Use `pg_terminate_backend` only if cancel does not work after 30 seconds.
3. Pause non-urgent bulk processing by setting the feature flag `payhub.bulk.intake.paused=true` in the configuration service. Customer single payments take priority.
4. Scale the orchestrator pods only if the database has spare capacity. Adding pods adds connections, which can make things worse:
   ```
   kubectl -n payhub scale deploy/payhub-orchestrator --replicas=<current+2>
   ```
5. If the pool is the limit and the database is healthy, raise the pool size through the approved emergency change route in POL-005. Do not edit the deployment by hand.
6. Once pending connections fall to zero for 10 minutes, unpause bulk intake and watch the dashboard for another 15 minutes.
7. Record times, queries cancelled and settings changed in the incident ticket.
