# Helix Mobile login failures after signing key rotation

## Summary

On Friday 4 September 2026 many customers could not log in to Helix Mobile between 07:00 and 08:50. The identity platform behind HelixID, which also issues customer session tokens, rotated its token signing key at 07:00 as planned. The Edge Gateway was still using a cached copy of the old public keys and rejected every token signed with the new key.

Customers who were already logged in kept working until their session expired. Helix Online was not affected because it checks keys directly with the identity platform. This was not a payment failure incident, although customers who could not log in could not make payments in the app.

## Root cause

The Edge Gateway caches the identity platform's public key set to avoid calling it on every request. The cache refresh time was 24 hours. The key rotation published the new key and started using it at the same moment, so the Edge Gateway had no copy of it.

The change was approved under POL-005 and had a rollback plan, but the plan only covered the identity platform. Nobody checked how the systems that validate tokens would pick up the new key. The previous rotation, 12 months earlier, happened when the Edge Gateway still called the identity platform directly, so this had never been tested.

**Cause category:** HelixID signing key rotation not coordinated with the Edge Gateway key cache.

## Resolution

Site Reliability flushed the key cache on all Edge Gateway nodes, which loaded the new key. Customers were able to log in straight away. No key rollback was needed.

## Lessons learned

- A rollback plan must cover every system the change touches, not only the system being changed.
- Caches that hold security keys need a way to pick up a new key without waiting a full day.
- Rolling back is not always safe. In this case it would have broken the customers who had just logged in.
- Rare yearly changes need a dry run in pre-production, because the setup around them may have changed since last time.
