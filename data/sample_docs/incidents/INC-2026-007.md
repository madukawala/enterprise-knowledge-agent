# Instant payments rejected after routing rule change

## Summary

On Tuesday 17 February 2026 a change to the PayHub routing rules for instant payments was deployed straight to production at 10:32. The new rules contained an error in a sort code range, so instant payments to about 40% of receiving banks were sent down the wrong route and rejected with "invalid routing". The change was rolled back at 11:38. Payments to other banks were not affected.

The change was made without a canary release and without a written rollback plan.

## Impact

| Measure | Value |
|---|---|
| Duration of customer impact | 10:34 to 11:38 (1 hour 4 minutes) |
| Instant payments rejected | about 9,840 |
| Customers affected | about 7,150 |
| Value of rejected payments | about £6.3 million |
| Money lost | none. Rejected payments were never debited. |
| Complaints | 410 |

Customers saw an error message in Helix Mobile and Helix Online saying the payment could not be made. Many tried again and some switched to a standard next-day payment.

## Root cause

The change added a new route for instant payments to a group of receiving banks that had moved to a new FastLane participant connection. The sort code range was typed as `40-00-00` to `49-99-99` instead of `40-00-00` to `40-99-99`. Payments to every bank in the wider range were sent to the new route, which did not recognise them.

The routing rules are held as configuration, not code. The team saw the change as low risk and deployed it straight to production. It was not tested in pre-production with real sort codes, it was not released to a small share of traffic first, and there was no prepared rollback.

**Cause category:** configuration change deployed without a canary (first occurrence in the last year).

## Resolution

We restored the previous routing rules from version control and redeployed them. The correct change was released on 24 February, first to 5% of traffic for one hour, then to all traffic, with no errors.

## Lessons learned

- Configuration changes can break production just as easily as code changes. They need the same care.
- A canary at 5% of traffic would have limited the damage to a few hundred payments and shown the problem within minutes.
- Rolling back took 23 minutes because nobody had planned how to do it.
- Later configuration incidents (INC-2026-027 and INC-2026-043) show the same cause appearing in other systems, so this lesson needs to apply bank-wide, not only to routing rules.
