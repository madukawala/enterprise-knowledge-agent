# Quarter-end PayHub slowdown

## Summary

On Monday 29 September 2025, the last working day of the quarter, PayHub slowed down sharply between 16:10 and 17:25. Payment submissions from Helix Mobile and Helix Online took up to 9 seconds at the 95th percentile instead of the usual 0.8 seconds, and some requests timed out. No payments were lost and almost all customers who saw a timeout were able to pay on a second attempt.

Looking back, this was the first sign of the PayHub database connection pool problem that later caused INC-2026-003 and several other month-end incidents.

## Impact

| Measure | Value |
|---|---|
| Duration | 16:10 to 17:25 (1 hour 15 minutes) |
| Payment submissions that timed out | about 1,350 |
| Customers affected | about 1,100 |
| Payments lost or duplicated | none found |
| Bulk payment files | 212 files received after the 14:00 bulk cut-off (POL-007) validated late. All were ready for next-day processing as normal. |

## Timeline

| Time | Event |
|---|---|
| 15:45 | Quarter-end bulk payment files from business customers start arriving in volume. |
| 16:10 | PayHub submission latency starts to climb. |
| 16:25 | Latency alert (p95 above 3 seconds) pages the Payments Platform on-call engineer. |
| 16:40 | On-call sees `payhub-db` connection pool usage at 190 to 196 of 200 connections. |
| 16:55 | A long-running query on the `payment_instructions` table is identified in the database slow log. |
| 17:05 | Bulk file intake throttled to two files at a time to reduce load. |
| 17:25 | Volumes fall after the bulk peak. Latency back to normal. Incident closed. |

## Root cause

During the bulk payment peak, PayHub held database connections open for much longer than usual. The main reason was a duplicate-check query on the `payment_instructions` table that scanned a large part of the table for each new instruction. As the table had grown by about 40% since the start of the year, this query had slowly become more expensive.

With 200 connections per pod group, the pool came within a few connections of being full. Requests that could not get a connection quickly waited and then timed out at the channel.

**Cause category:** PayHub database connection pool pressure at peak (early warning, pool not fully exhausted).

## Resolution

Payments Operations throttled bulk file intake, which reduced the number of long queries running at the same time. The slowdown ended when the quarter-end peak passed. No change was made to PayHub itself on the day.

## Lessons learned

- Because there was no outage, the follow-up actions were given low priority and slipped. Four months later the same pattern caused a SEV1 on salary day (INC-2026-003). A near-miss at a peak date should be treated as a warning of a bigger failure at the next peak.
- Throttling bulk intake helped, but it is a manual workaround and depends on someone noticing in time.
- We had no runbook for connection pool problems. RB-001, PayHub Database Connection Pool Exhaustion, was eventually written in March 2026 after INC-2026-003 and INC-2026-009.
