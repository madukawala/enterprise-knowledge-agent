# End-of-day batch overrun delayed statements

## Summary

The CoreLedger end-of-day (EOD) batch that started at 23:30 on Sunday 1 March 2026 finished at 07:05 on Monday 2 March, 1 hour 35 minutes after the 05:30 deadline. Balances in Helix Mobile and Helix Online showed the previous day's figures until the batch finished, and monthly e-statements were delivered a day late. The Scheduler 06:00 run was held until the batch completed, so standing orders were paid later than the 07:30 target but none failed.

This was not a payment failure incident. RB-006, End-of-Day Batch Overrun, was followed and worked as written.

## Impact

| Measure | Value |
|---|---|
| Batch overrun | 1 hour 35 minutes past 05:30 |
| Customers with stale balances shown in app and web | all retail customers, 05:30 to 07:05 |
| Monthly e-statements delayed by one day | about 410,000 customers |
| Standing orders delayed (not failed) | about 296,000, paid between 07:15 and 07:58 |
| Payments failed | none |
| Complaints | 85 |

## Timeline

## Root cause

During a CoreLedger patch on 26 February, a batch parameter file was replaced with the vendor default. This reset the thread count for the interest accrual step from eight to one. On normal nights the step finishes quickly enough on one thread for nobody to notice. On the month-end run, with interest capitalisation for all savings accounts, the step took 4 hours 50 minutes instead of about 50 minutes.

Volume was also around 12% higher than a normal month-end because of the bulk payment backlog from INC-2026-009 on 27 February.

**Cause category:** end-of-day batch overrun caused by a configuration reset during patching.

## Resolution

The batch was allowed to finish. The thread count was set back to eight on 2 March and the parameter file was added to the CoreLedger configuration repository so that patches cannot overwrite it silently. The 3 March batch finished at 03:12.

## Lessons learned

- RB-006 worked. Holding the Scheduler run stopped standing orders from running against stale balances.
- Patches can change configuration we do not expect. We need to check what a patch touches, not just that it installed.
- An alert at 03:40 left little time to act. Per-step alerts would have flagged the slow step around 02:30.
