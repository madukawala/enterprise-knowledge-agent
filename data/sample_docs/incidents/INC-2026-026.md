# Payroll file submission delayed

## Summary

On Wednesday 24 June 2026 the monthly staff payroll file sent from PeopleHub to PayHub was rejected at 16:02 because the payment dates were in the wrong format. The problem came from a PeopleHub upgrade on 20 June. HR Systems fixed the export and resubmitted the file at 19:40, and it was accepted for processing. All 6,240 Helix staff were paid on time on payday, Friday 26 June.

No customer payments were affected. This was the first use of RB-010, Payroll File Submission Failure, which had been published two days earlier.

## Impact

| Measure | Value |
|---|---|
| File rejected at | 16:02 |
| File accepted at | 19:40 (3 hours 38 minutes later) |
| Staff in the payroll file | 6,240 |
| Total value of the file | about £21.3 million |
| Staff paid late | none |
| Customer impact | none |

The main impact was staff time and risk. If the file had not been accepted by the 16:00 cut-off on 25 June, staff salaries would have been paid a day late.

## Root cause

The PeopleHub upgrade on 20 June changed the default date format in the payment export template. The upgrade was tested by HR Systems, but the testing covered screens and reports, not the payroll export. The export is only used once a month, so the fault did not show until the June run.

PayHub validated the file correctly and rejected it, which is the intended behaviour.

**Cause category:** PeopleHub export defect after an upgrade (not one of the recurring payment-failure causes).

## Resolution

HR Systems set the export date format back to `YYYY-MM-DD` in the PeopleHub template, produced a new file and checked the totals and line count against the payroll report. The file was resubmitted and accepted. The template setting is now locked so upgrades cannot change it.

## Lessons learned

- RB-010 was published just in time and gave the team a clear order of checks.
- Upgrade testing must cover every output that leaves the system, including ones used only once a month.
- Sending the file a day earlier gives more room before the 16:00 cut-off to fix problems without risking late salaries.
- Fixing the source was better than editing the file by hand, which would have needed extra controls.
