# Month-end bulk payments delayed

## Summary

On Friday 27 February 2026, the last working day of the month, PayHub ran out of database connections again between 12:20 and 14:55. Bulk payment files from business customers were held up, and some retail payments from Helix Mobile and Helix Online failed. Most bulk payments went out the same day, but about 2,300 payment lines could not be validated before the 14:00 bulk cut-off in POL-007 and were paid on Monday 2 March.

This is the second connection pool outage in four weeks, after the salary-day incident INC-2026-003. The index added after that incident fixed one slow query but not the one used for bulk files. The load test promised before month-end had not been run.

|---|---|

| Bulk files delayed | 4,120 files, about 612,000 payment lines |

## Root cause

When a bulk file arrives, PayHub checks every line against recent instructions in the `payment_instructions` table to catch duplicate files. This query filters on batch reference and value date, and no index covered those columns. The index added after INC-2026-003 was for single payment duplicate checks and did not help here.

At month-end, large files from many customers ran this query at the same time. Each held a connection for several seconds, and the 200-connection pool ran out.

The load test agreed after INC-2026-003 had been scheduled for March, after this month-end, so the problem was not found in advance.

**Cause category:** PayHub database connection pool exhaustion at peak (second occurrence, after INC-2026-003; early warning in INC-2025-031).

## Resolution

Payments Operations throttled bulk intake, which let retail traffic recover. An index on `payment_instructions (batch_reference, value_date)` was added on 28 February under an emergency change. Lines that missed the cut-off were sent first thing on 2 March, and fees for late payments were refunded to business customers who asked.

## Lessons learned

- Fixing the one query we saw last time was not enough. We need to look for the whole class of problem.
- Promised actions must be finished before the next peak, not scheduled after it.
- Throttling bulk intake protects retail customers and should be a standard first step. It is now step 2 in RB-001.
