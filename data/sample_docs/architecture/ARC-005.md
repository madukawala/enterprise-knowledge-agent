# Payment Status Service and Event Streaming

## Purpose and scope

This document describes the Payment Status Service (PSS) and the Kafka event streams it depends on. PSS keeps the status of every payment up to date for customers and staff, and sends push, SMS and email notifications when a payment completes or fails. The document covers the topics, consumers, data stores and known risks. It does not cover how PayHub decides a payment's outcome; see ARC-001.

## Context

Before PSS, Helix Mobile and Helix Online asked PayHub directly for payment status, which added read load to `payhub-db`. PSS was introduced in early 2025 so that status reads and notifications are handled outside PayHub. PayHub, IPG and the Scheduler publish an event whenever a payment changes state. PSS consumes these events and maintains a read-optimised status store.

On a normal day PSS processes about 6 million events. On salary day this rises to about 13 million, with peaks of 2,500 events per second between 08:00 and 10:00.

## Components

| Component | Description |
|---|---|
| Kafka cluster | Three brokers at the primary site, replicated to the secondary site. Managed by Site Reliability. |
| Topic `payments.status` | 24 partitions, keyed by payment reference so events for one payment stay in order. Retention 7 days. |
| Topic `payments.status.dlq` | Dead-letter topic for events that fail processing three times. |
| `pss-consumer` | Consumer group that reads `payments.status`, updates the status store and triggers notifications. Fixed at 8 pods. |
| Status store | Postgres database with the latest status and history per payment. |
| `pss-api` | Read API used by the channels and by the contact centre desktop. |
| Notification adapter | Sends push, SMS and email through the bank's messaging providers. |

## Data flow

1. PayHub writes a status change to `payment_events` and publishes an event to `payments.status` in the same transaction using the outbox pattern.
2. The event carries the payment reference, the new status, the reason code and a timestamp.
3. A `pss-consumer` pod reads the event from its assigned partition.
4. The consumer updates the status store. Events older than the stored status are ignored, so out-of-order delivery after a retry does not move a payment backwards.
5. If the new status is final (completed, failed or returned), the consumer calls the notification adapter.
6. The consumer commits its offset after both steps succeed.
7. Helix Mobile and Helix Online read the status from `pss-api`.

## Resilience and failure modes

| Failure | Effect |
|---|---|
| A consumer pod crashes | Its partitions are reassigned to other pods within 30 seconds |
| Notification provider slow | Consumers wait on each call, so status updates slow down too |
| Bad message on a partition | Retried three times, then moved to the dead-letter topic |
| Kafka broker lost | Partitions move to remaining brokers; short pause in consumption |
| Status store slow | Consumer lag builds on all partitions |

If consumers fall behind, payments that have already completed show as "pending" in the channels. Customers may then send the same payment again.

## Security

- Producers and consumers authenticate to Kafka with mTLS client certificates per service.
- Topic access is controlled by access control lists. Only PayHub, IPG and the Scheduler can write to `payments.status`.
- Events carry the payment reference and amount but not full account numbers.
- Status data is classified confidential under POL-003.

## Known limitations

- The consumer group is fixed at 8 pods. There is no autoscaling on lag, and scaling up is a manual step.
- Status updates and notifications run in the same consumer, so a slow notification provider delays status updates.
- PayHub does not check for duplicate payment requests. If a customer resends a payment because the status looks stuck, both payments are sent.
- Lag alerts exist but the thresholds have not been tuned for salary-day volumes.
- There is no runbook yet for consumer lag.
