# PayHub Payments Platform Overview

## Purpose and scope

This document describes PayHub, the bank's payments orchestration hub. It is the starting point for engineers joining Payments Platform and for teams that integrate with PayHub. It covers the main services, the database, the systems PayHub talks to and how a payment moves through it. Detailed designs for the Instant Payments Gateway and the Payment Status Service will be written up as separate documents.

## Context

PayHub replaced the old payments mainframe module in 2024. It takes payment instructions from Helix Mobile, Helix Online, business bulk files and the Scheduler, checks them, reserves funds in CoreLedger and sends them to the right payment route. About 1.4 million payments pass through it on a normal weekday, rising to around 3 million on salary day and at month-end.

PayHub handles:

- single transfers between Helix accounts and to other banks,
- instant payments through IPG and FastLane,
- bulk payments from business customers and the monthly payroll file from PeopleHub,
- standing orders and scheduled payments released by the Scheduler.

## Components

| Component | Description | Runs on |
|---|---|---|
| `payhub-api` | REST API behind the Edge Gateway. Validates requests and creates payment instructions. | Kubernetes, namespace `payhub` |
| `payhub-orchestrator` | State machine that drives each payment through checks, funds reservation and routing. | Kubernetes |
| `payhub-bulk` | Parses bulk and payroll files, splits them into single instructions. | Kubernetes |
| `payhub-router` | Chooses the payment route (internal book transfer, FastLane, standard clearing) using routing rules. | Kubernetes |
| `payhub-db` | Postgres database holding `payment_instructions`, `payment_events` and reference data. | Dedicated database cluster |
| Connection pool | HikariCP pool in each service. Default 200 connections per pod group. | In service |
| Configuration service | Routing rules, limits and feature flags. | Shared platform service |

## Data flow

1. A customer submits a payment in Helix Mobile. The Edge Gateway authenticates the request and forwards it to `payhub-api`.
2. `payhub-api` validates the payee details and limits, writes a row to `payment_instructions` with status `RECEIVED` and returns a reference to the customer.
3. `payhub-orchestrator` picks up the instruction and asks Sentinel for a fraud score where the payment type requires it.
4. The orchestrator calls CoreLedger to reserve funds on the debit account.
5. `payhub-router` selects the route. Instant payments go to IPG; others go to the standard clearing file or are booked internally.
6. Each status change is written to `payment_events` and published to the Kafka topic `payments.status`, which the Payment Status Service consumes.
7. On final confirmation from the route, CoreLedger posts the debit and the instruction is marked `COMPLETED`, or `FAILED` with a reason code.

## Resilience and failure modes

- All services run at least three pods across two availability zones.
- `payhub-db` has a synchronous standby in the same data centre and an asynchronous copy at the secondary site.
- If Sentinel does not respond within 300 ms, the orchestrator applies the fallback rules for that payment type.
- If CoreLedger is unavailable, new payments are held in `RECEIVED` for up to 10 minutes and then failed.
- Database connection pool exhaustion is the main risk at peak. Every service shares the same primary database, so a slow query affects all payment types.

## Security

- All traffic between services uses mTLS inside the service mesh.
- Only `payhub-api` is reachable from the Edge Gateway.
- Database credentials are issued per service from the secrets vault and rotated every 30 days.
- Operator screens require HelixID sign-in and a Payments Operations role.
- Payment data is classified confidential under POL-003.

## Known limitations

- A single primary database serves both writes and read-heavy screens such as payment history.
- The `payment_instructions` table has grown to about 900 million rows. Some status queries do not use an index and slow down at month-end.
- The pool size of 200 was set from 2024 load tests and has not been tested against current salary-day volumes.
- Routing rule changes take effect immediately across all pods.
