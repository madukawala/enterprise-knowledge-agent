# Sentinel Fraud Screening Engine Design

## Purpose and scope

This document describes the design of Sentinel, the bank's real-time fraud screening engine. It covers how Sentinel receives transactions, how it scores them, how decisions are returned and how rules and thresholds are managed. It is restricted. Knowledge of the scoring approach and thresholds would help fraudsters avoid detection. Share only with people who need it for their role, in line with POL-003.

## Context

Sentinel screens card-not-present card transactions from CardSwitch and outbound instant payments from PayHub before they reach IPG. It does not screen chip and PIN transactions, which rely on the card cryptogram and network rules. Sentinel scores about 1.1 million transactions a day and must answer within 150 ms for cards and 300 ms for instant payments.

Fraud losses on card-not-present payments were about 0.07% of value in 2024. The target for 2025 is below 0.05%, without raising false declines above 1.5% of genuine transactions.

## Components

| Component | Description |
|---|---|
| Scoring API | Receives a transaction, gathers features and returns a decision. Four pods per site in Zone 4. |
| Feature store | In-memory store with rolling customer and device features: spend in the last hour, new payee flag, device age, distance from usual location. Updated within 2 seconds of each event. |
| Scoring model | Gradient-boosted model retrained monthly on labelled fraud cases. Produces a score from 0 to 1,000. |
| Rules layer | Hard rules that override the score, for example known compromised merchant lists and mule account lists. |
| Threshold table | Score bands that map to approve, step-up or decline, per channel and merchant category. |
| Case manager | Queue for fraud analysts to review referred payments and confirmed fraud. |

## Data flow

1. CardSwitch or PayHub sends a scoring request with transaction details, device data where available and customer reference.
2. The scoring API reads current features for the customer, card and device from the feature store.
3. The rules layer runs first. If a hard rule matches, Sentinel returns its decision straight away.
4. Otherwise the model produces a score.
5. The score is compared to the threshold table for the channel. Current card-not-present bands are: below 620 approve, 620 to 849 step-up authentication, 850 and above decline. Instant payments to a new payee use a lower decline band of 800.
6. Sentinel returns the decision and a reason code. Step-up for cards triggers a challenge in Helix Mobile; for instant payments it triggers a confirmation screen with a scam warning.
7. The transaction and outcome are written to the feature store and to the case manager if referred.

## Resilience and failure modes

| Failure | Behaviour |
|---|---|
| Sentinel times out | Caller applies fallback rules: cards approve up to 150 in local currency per transaction, otherwise decline; instant payments to known payees allowed, new payees held for 10 minutes |
| Feature store unavailable | Model runs with reduced features; thresholds automatically raised by 50 points |
| Model file corrupt | Previous model version loaded automatically |
| Threshold table changed in error | Approval or decline rates shift immediately across the channel |

Sentinel runs active-active across both sites. Each site can handle full peak load.

## Security

- Access to the threshold table and rules layer is limited to six named staff in Fraud and Security and Fraud analytics, through privileged access under POL-006.
- Every change to rules or thresholds is logged with the person, time and old and new values.
- Model training data is pseudonymised. Analysts see customer details only through the case manager.
- Sentinel does not store full card numbers; it uses tokens from CardSwitch.

## Known limitations

- Threshold changes take effect immediately in production. There is no canary or shadow mode for thresholds, only for new models.
- The threshold table is edited by hand in the admin console. A wrong value cannot be rolled back with one command.
- Fallback rules for card timeouts are generous and could be exploited during an outage.
- Monthly retraining depends on fraud cases being labelled within 30 days; backlogs reduce model quality.
- Monitoring alerts on decline rate but not on sudden changes in step-up rate.
