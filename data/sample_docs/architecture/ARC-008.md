# Helix Mobile and Helix Online Channel Architecture

## Purpose and scope

This document describes how the bank's two digital channels, Helix Mobile and Helix Online, are built and how they reach back-end systems. It covers the client applications, the Edge Gateway, customer authentication and the channel back ends. It is written for engineers and architects working on any system that serves the channels. Back-end systems are described in their own architecture documents.

## Context

About 1.7 million customers use Helix Mobile at least once a month and about 600,000 use Helix Online. Mobile accounts for 82% of logins. Both channels offer the same core features: balances and transactions, transfers and instant payments, card management, standing orders and secure messages. Business customers also use Helix Online for bulk payment uploads.

Peak traffic is around 9,000 requests per second, usually on salary day between 07:00 and 09:00.

## Components

| Component | Description | Owner |
|---|---|---|
| Helix Mobile app | Native apps for the two major mobile platforms. Release every two weeks. | Digital Channels |
| Helix Online | Single-page web application served from the content delivery layer. | Digital Channels |
| Edge Gateway | API gateway. Terminates TLS, applies rate limits, validates tokens and routes requests. | Site Reliability |
| Customer identity service | Customer login, device binding, one-time passcodes and token issuing. Signs access tokens with keys rotated every 6 months. | Fraud and Security |
| Channel back ends | Thin services per feature that combine calls to PayHub, CoreLedger, CardSwitch and other systems. | Digital Channels |
| HelixID | Staff single sign-on. Used for contact centre and operations tools, not for customers. | Fraud and Security |

## Data flow

A customer making a transfer in Helix Mobile:

1. The customer opens the app and unlocks it with biometrics or a PIN. The app holds a device-bound key registered at enrolment.
2. The app requests an access token from the customer identity service, signing the request with the device key.
3. The identity service checks the device and session and issues a short-lived access token (10 minutes) and a refresh token.
4. The app calls the Edge Gateway with the token.
5. The Edge Gateway validates the token signature against the identity service's published keys, applies rate limits and routes the request to the payments channel back end.
6. The channel back end calls PayHub to create the payment and returns the reference to the app.
7. The app polls for status until the payment is final.

Helix Online follows the same pattern, except that login uses a one-time passcode sent to the registered device instead of a device key.

## Resilience and failure modes

| Failure | Effect |
|---|---|
| Edge Gateway node lost | Traffic moves to the remaining nodes; minimum of six nodes over two zones |
| Identity service down | New logins fail; existing sessions continue until their token expires |
| Token signing key mismatch | All token validation fails at the Edge Gateway, so every logged-in call is rejected |
| A back end slow | Edge Gateway times out the call after 15 seconds; other features keep working |
| App release defect | Phased rollout allows the release to be halted at 10% of users |

## Security

- All traffic is over TLS 1.2 or later. Certificate pinning is used in Helix Mobile.
- Rate limits apply per customer and per device to slow down credential stuffing.
- Payments to new payees and high-value transfers require step-up confirmation.
- Staff tools use HelixID and are not reachable from the public internet.
- Use of bank devices and systems by staff follows POL-002.

## Known limitations

- The Edge Gateway caches the identity service's public keys for 24 hours. A key rotation must publish the new key well before it is used, or validation will fail.
- Status is polled by the app rather than pushed, adding read load to back-end systems.
- Helix Online still uses a session cookie for some legacy pages.
- Both channels depend on a single identity service cluster at the primary site.
