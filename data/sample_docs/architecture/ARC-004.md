# CoreLedger and the End-of-Day Batch

## Purpose and scope

This document describes CoreLedger, the bank's core banking ledger, and the nightly end-of-day (EOD) batch that closes each business day. It is aimed at engineers in Core Banking and in teams that read or post to the ledger. It covers account and balance data, the online posting API and the batch stages. Interest product rules are owned by the savings and lending product teams and are only summarised here.

## Context

CoreLedger holds every customer account at Helix Commercial Bank: around 2.1 million retail customers and 48,000 business customers, with about 3.4 million accounts in total. It is the single source of truth for balances. PayHub, CardSwitch, Helix Mobile and Helix Online all depend on it.

During the day CoreLedger accepts holds and postings in real time. Overnight, the EOD batch completes the day's accounting. The batch must finish by 05:30 so that balances are final before morning traffic and before the Scheduler's 06:00 standing order run.

## Components

| Component | Description |
|---|---|
| Ledger database | Postgres cluster with `accounts`, `ledger_postings`, `holds` and `balances`. Primary and synchronous standby at the primary site. |
| Posting API | Online API for holds, releases and postings. Used by PayHub and CardSwitch. |
| Account API | Read API for balances and transaction history. Used by the channels through the Edge Gateway. |
| Batch engine | Runs the EOD jobs in a fixed order with checkpoints. Controlled with the `eodctl` tool. |
| Reporting replica | Read-only copy for reports, statements and finance extracts. |
| Batch monitor | Publishes stage progress and predicted finish time to Prometheus and the "CoreLedger EOD" dashboard. |

## Data flow

The EOD batch starts at 23:30 when the business date is closed for online posting. Online posting continues against the next business date.

1. **Cut-off.** New postings are written with the next business date. Holds from card authorisations stay in place.
2. **Transaction posting** (target finish 01:45). Clearing files, card settlement files and internal transfers are posted to `ledger_postings`.
3. **Fees and charges.** Account fees due that day are calculated and posted.
4. **Interest calculation** (target finish 03:15). Daily interest is accrued on every interest-bearing account. Monthly or quarterly interest is capitalised on the due date.
5. **Statement extract** (target finish 04:30). Statement lines are written to the reporting replica for the statement service.
6. **Balance roll and date roll** (target finish 05:00). Closing balances become opening balances for the new business date.
7. **Completion signal.** The batch publishes `EOD_COMPLETE` with the business date. The Scheduler waits for this signal before releasing standing orders.

## Resilience and failure modes

- Each job writes a checkpoint every 50,000 records. A failed job can restart from its last checkpoint without double-posting.
- The ledger database standby takes over automatically if the primary fails. A failover during the batch pauses the batch for about 10 minutes.
- If the batch overruns, balances shown in the channels may be a day old and the Scheduler run is delayed.
- Month-end and quarter-end volumes are about 40% higher than normal and use most of the spare time in the window.
- Heavy reporting queries run against the primary by mistake can slow the posting stage.

## Security

- Only the Posting API service accounts can write to the ledger. No direct database writes are allowed outside approved break-glass procedures.
- Batch operator access needs HelixID sign-in and the Core Banking batch role.
- All postings are signed with the calling service's identity and kept for audit for seven years.
- Balance and transaction data is classified confidential under POL-003.

## Known limitations

- The batch is largely sequential. Interest calculation cannot start until all posting is finished.
- There is only about 30 minutes of headroom on month-end nights.
- The batch monitor predicts finish time from the last four weeks, so it reacts slowly to sudden volume jumps.
- There is no automatic way to hold the Scheduler if the batch is late; it relies on the on-call engineer.
