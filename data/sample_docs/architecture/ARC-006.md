# Network Segmentation and mTLS Certificate Management

## Purpose and scope

This document describes how the bank's internal network is divided into security zones, and how mutual TLS (mTLS) certificates are issued, stored, deployed and renewed between systems. It covers internal service certificates and the external certificates used to connect to the card networks and to NorthClear. It is confidential.

## Context

The bank must keep the card environment separate from general corporate systems, and must be able to show auditors which systems can talk to which. We do this with network zones and firewall rules, backed by mTLS so that each connection proves the identity of both ends.

Internal certificates are short-lived and renewed automatically. External certificates, issued by third parties, are long-lived (usually 12 or 24 months) and renewed by hand.

## Components

| Zone or component | Contents | Notes |
|---|---|---|
| Zone 0, external edge | Edge Gateway, web application firewall | Only zone reachable from the internet |
| Zone 1, channels | Helix Mobile and Helix Online back ends | Calls Zone 2 only through the Edge Gateway |
| Zone 2, payments | PayHub, IPG, PSS, Scheduler, Kafka | Private link to NorthClear from IPG only |
| Zone 3, card environment | CardSwitch, Network Gateway, card store, card HSMs | Strictest controls. Private circuits to card networks. |
| Zone 4, core | CoreLedger, Sentinel | Reached only on named ports from Zones 2 and 3 |
| Zone 5, corporate | Staff devices, PeopleHub, email | No direct route to Zones 2 to 4 |
| Internal certificate authority | Issues service certificates for the service mesh | Root key offline, issuing keys in HSM |
| Certificate inventory | Spreadsheet listing external certificates, owners and expiry dates | Maintained by each owning team |
| Secrets vault | Stores certificate bundles and references to HSM keys | Path per system, for example `cards/ngw/client-cert` |

## Data flow

Internal service certificate lifecycle:

1. A new service is registered in the service mesh with its identity.
2. The mesh requests a certificate from the internal certificate authority. Validity is 72 hours.
3. The mesh renews the certificate automatically after 48 hours and reloads it without a restart.
4. Expired or revoked certificates are refused at the next connection.

External certificate lifecycle (card networks, NorthClear):

1. The owning team generates a key pair inside the HSM.
2. A certificate signing request is sent to the third party's portal, approved by two people.
3. The signed certificate and its intermediate chain are stored in the vault as a new version.
4. The owning team deploys the bundle to each site where the connection is terminated.
5. The certificate inventory is updated with the new expiry date and the next renewal owner.

## Resilience and failure modes

| Failure | Effect |
|---|---|
| Internal CA unavailable | Existing certificates keep working for up to 24 hours; new pods cannot start |
| External certificate expires | The third party refuses the connection; for CardSwitch all card authorisations at that site fail |
| Intermediate missing from bundle | Some peers cannot build the chain; failure may affect one site only |
| Certificate deployed to one site only | The other site fails when the old certificate expires |
| Firewall rule removed in error | Connection fails between zones; caught by synthetic checks every 60 seconds |

## Security

- Private keys for external certificates never leave the HSM.
- Firewall changes between zones need approval from Fraud and Security under POL-005.
- All cross-zone traffic is logged and kept for 13 months.
- Access to the vault paths is limited to the owning team's service accounts and two named administrators per team.

## Known limitations

- External certificate expiry is tracked in a spreadsheet. There is no automated alert when a certificate is close to expiry.
- Each site's Network Gateway is configured separately, so there is no check that both sites present the same certificate.
- Renewal knowledge sits with a small number of people in Cards Platform and Payments Platform.

Fraud and Security has proposed an automated certificate monitor that reads every external endpoint daily and alerts at 60, 30 and 7 days. It is not yet funded.
