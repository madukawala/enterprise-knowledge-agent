# Card Authorisation Flow through CardSwitch

## Purpose and scope

This document explains how a card authorisation request reaches Helix Commercial Bank and how CardSwitch decides to approve or decline it. It covers debit and credit cards issued by the bank. It does not cover merchant acquiring, which the bank does not offer, or the details of fraud scoring, which Fraud and Security document separately.

## Context

When a Helix card holder pays at a shop or online, the merchant's bank sends an authorisation request through the card network to us as issuer. We must reply within the network's time limit, normally 2 seconds end to end, of which our own budget is 800 ms. CardSwitch processes about 3.5 million authorisations on a busy day, with peaks of 450 per second on Saturday afternoons and in late December.

CardSwitch runs in two sites, primary and secondary. Both sites are active and the card networks share traffic between them.

## Components

| Component | Description |
|---|---|
| Network Gateway | Terminates the connections to the card networks. Uses mutual TLS with a client certificate issued by each network. One gateway pair per site. |
| CardSwitch core | Parses the network message, looks up the card, applies card controls and limits, and builds the response. |
| Card store | Postgres database with card records, status and controls set in Helix Mobile. Replicated between sites. |
| HSM cluster | Hardware security modules that verify PINs, card cryptograms and CVV values. Two HSMs per site. |
| Sentinel | Fraud screening engine. Called for card-not-present and selected high-risk transactions. |
| CoreLedger API | Checks available balance for debit cards and places a hold. |
| Credit limit service | Checks available credit for credit cards. |

## Data flow

1. The card network sends an authorisation request to the Network Gateway over the mTLS connection.
2. The gateway checks the message format and passes it to CardSwitch core at the same site.
3. CardSwitch looks up the card in the card store. Blocked, lost or frozen cards are declined at this step.
4. For chip and PIN transactions, CardSwitch asks the HSM to verify the PIN block and the chip cryptogram.
5. Card controls are applied, for example online payments switched off or a spending limit set by the customer.
6. For card-not-present transactions, CardSwitch calls Sentinel, which returns approve, decline or step-up.
7. For debit cards, CardSwitch calls CoreLedger to check balance and place a hold. For credit cards, it calls the credit limit service.
8. CardSwitch builds the response with the approval code or decline code and returns it through the Network Gateway.
9. The authorisation is written to the card store and an event is sent for notifications.

## Resilience and failure modes

| Failure | Effect | Mitigation |
|---|---|---|
| One site lost | Network sends all traffic to the other site | Each site sized for 100% of peak |
| HSM unavailable | PIN and cryptogram checks fail | Second HSM in each site; cross-site HSM call as last resort |
| Sentinel slow | Card-not-present payments delayed | 150 ms timeout, then fallback rules |
| CoreLedger slow or down | Debit cards cannot be checked | Stand-in limits applied for low-value transactions |
| Network Gateway certificate invalid | Network rejects our connection, all authorisations at that site fail | Manual renewal tracked by Cards Platform |
| Whole switch down | No responses | Network stand-in processing with agreed limits |

## Security

- PINs and card keys are only ever handled inside the HSM.
- Network Gateway private keys are stored in the HSM, not on disk.
- Card numbers are tokenised in logs and in the card store indexes.
- The card environment is a separate network segment with its own firewall rules, owned by Fraud and Security.

## Known limitations

- Certificate renewal for the Network Gateway is manual and tracked in a spreadsheet.
- The two sites are configured separately, so a change applied to one can be missed on the other.
- Stand-in limits at the network have not been reviewed since 2023.
- HSM firmware updates need a maintenance window and cannot be rolled out one HSM at a time without a manual traffic move.
